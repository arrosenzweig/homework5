3 · Why one agent with tools would have been simpler

For this workload, a single agent holding all ten MCP tools would have been simpler, cheaper and nearly as safe. The evidence is on this page.

The concrete waste

Ticket #102 ran the identical tool call twice. Facilities called get_cash_and_obligations() with no arguments, and accounting called get_cash_and_obligations() with no arguments — the same zero-argument call, in the same run, seconds apart, returning identical data. Neither can see the other's results, so the second call was pure duplication. One agent calls it once.

Delegation, not tool use, is where the tokens go. #102 used 8 model requests for a ticket whose real work was: read the lease, compare to the balance. Each ask_* costs a request to compose the question, a full nested agent run, and a request to read the report back. A single agent would have done #102 in roughly 3 requests. The 22,577-token floor on the simplest ticket is almost entirely delegation overhead.

Six prompt files instead of one. _shared.md plus five desk prompts, and the anti-hallucination rules have to be repeated into every agent's context on every request. One agent means one prompt loaded once.

What the split actually buys

Two things, and it is worth being honest that only one of them is structural. Least privilege: customer service cannot move money because DESK_TOOLS never shows it record_payment — a real guarantee, not a prompt instruction. Separation of verify from pay: facilities established the $2,400 and had no payment tool; accounting paid and could not have invented the obligation. On #102 that separation did visibly work.

But the money was never really protected by the agent split. It was protected by the MCP write tools, which refuse an overdraft, a double payment, or a wrong amount regardless of which agent calls them — as the approval tests showed when a human-approved $500 payment against the $840 invoice was still refused. The team is defence in depth. The depth is in the tools.

Verdict
At three tickets against a nine-table database, one agent with ten tools wins. The team earns its overhead only when desks need genuinely different authority, when they can run in parallel rather than in sequence, or when one desk's prompt grows too large to sit in a shared context — none of which is true of a shop with four SKUs.

4 · Three new problems our existing tools could already solve

a. Nothing warns anyone a SKU has hit zero

On this shift CC-TEE-WHITE size S was at 0 and CC-MUG-CREST is still at 0 — the mug has had no reprint, no invoice, and no ticket. The shop only discovered the tee problem because a customer complained. Solvable today: check_stock over each SKU plus find_vendor for the lead time plus post_desk_note to leave the warning. A scheduled run of the inventory desk alone would produce "CC-MUG-CREST OS is at 0; Elm City Gifts, 3-day lead" with no new tools at all.

b. Overdue bills are only noticed when something else touches them

Invoice 501 was 3 days overdue and surfaced only because ticket 101 happened to link to it. get_cash_and_obligations already returns is_overdue and days_until_due for every unpaid invoice, and record_payment already refuses to overdraw. Solvable today: a daily accounting run that lists everything overdue and proposes a payment order inside the current balance — exactly the reasoning it performed on #101, just unprompted by a ticket.

c. Every discount request is priced from scratch

On #103 accounting had to reach $50.00 itself. get_price_and_margin already scores any proposed price against unit_cost and returns above_cost. Solvable today: auto-score every price_override ticket on arrival, so a human opens it already knowing "$22.00 floor, $58.00 list, $50.00 leaves $28.00/unit". No new tools — just running the existing one before the ticket is read rather than after.

5 · Three problems we could not solve, and what they would need

a. Proving the rent notice is genuine

What happened: facilities stated plainly that the notice "cannot be independently authenticated beyond the matching lease record". The database stores no email, no sender address, no headers, no attachment — only tickets.notes reading "Email: shop rent due in 2 days." A landlord impersonation would have passed every check we ran, because the only check available was that a name matched.

Needed: a read_message(message_id) MCP tool over the actual mailbox returning sender, headers and attachments, plus a verification desk that compares the claim against the lease, the payment history, and the sending domain. The agent was not failing here — it correctly reported a limit of the data, and no amount of prompting fixes a missing table.

b. Telling the customer when the tee actually arrives

What happened: customer service refused to promise the 2026-09-02 date, correctly, because expected_delivery_date is derived as due_date + lead_days — arithmetic on an invoice, not a commitment from Bulldog Print Co. Tauhid Zaman could be told "out of stock" but not "it arrives Tuesday". The schema has no purchase_orders table at all.

Needed: a place_order / get_order_status pair talking to the vendor's system, backed by a real purchase-order table, plus a purchasing desk that owns POs end to end. Only then does a promised date come from the party who can keep it.

c. Choosing which bill to pay when both cannot be paid

What happened: accounting reached the $160 figure on two separate tickets and escalated both times without ever proposing a sequence. That was the right call, but it is also the shop's central question and the agents could not answer it. The reason is structural: the database records outflows only — invoices, leases, payments — and has no sales, orders, or revenue table. Nothing in the data says money is coming in, so no agent can responsibly rank payments.

Needed: a get_cash_forecast(days) tool over projected inflows (which requires a sales table that does not exist), plus a treasury desk carrying an explicit written policy — rent before trade payables, or rank by late penalty and relationship risk. Without both the forecast and the policy, "which bill first" is not an agent question; it is the owner's.

The common thread
  • All three failures are missing data, not missing intelligence. The agents correctly identified every one of these limits themselves rather than inventing an answer — which is the behaviour the tools were built to force.
  • Two of the three need a new table before a new tool makes sense: stored correspondence, and purchase orders. A tool over data that does not exist would just be a more confident guess.
